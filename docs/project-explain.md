

‏هذا المشروع عبارة عن تطبيق لعبة ثعبان كلاسيكية (Phosphor Snake Arcade) مصمم بأسلوب الخدمات المصغرة (Microservices) الحديثة، ومجهّز بالكامل للانتشار التلقائي على بيئة Kubernetes (k3s).

‏**مكونات النظام الأساسية**

‏| المكون | التقنية | الدور الأبرز في المشروع |

‏| **الواجهة الأمامية (Frontend)** | HTML5 Canvas + Nginx | تشغيل اللعبة والرسومات، والعمل كـ Reverse Proxy لتوجيه طلبات الـ API.

‏ |
‏| **خلفية النظام (Backend)** | Python (FastAPI + Uvicorn) | التحقق من صحة المدخلات، معالجة النقاط، وتوفير نقاط فحص الجاهزية (Probes).

‏ |
‏| **قاعدة البيانات (Database)** | Redis (Sorted Sets) | تخزين نتائج اللاعبين ولائحة المتصدرين وترتيبها تنازليًا بسرعة فائقة.

‏ |
‏| **البنية التحتية (K8s)** | Kubernetes Manifests | إدارة تشغيل الحاويات، التوسع التلقائي، والتخزين الدائم للبيانات.

‏*******************************كيف يعمل المشروع خطوة بخطوة؟*******************************

‏* **1. طلب اللعبة والوصول:** يوجه الـ Ingress (عبر Traefik) الزوار من النطاق `snake-game.duckdns.org` إلى خدمة الـ Frontend. يقدم خادم Nginx واجهة اللعبة للمتصفح مباشرة من خلال ملف `index.html`.


‏* **2. الاتصال وتفادي مشكلة CORS:** عندما يسجل اللاعب نقطة أو تنتهي اللعبة، يرسل المتصفح مسارًا نسبيًا `/api/score`. يتلقى Nginx الطلب ويوجهه داخليًا إلى `http://game-api:8000/api/score` عبر الـ Reverse Proxy. هذا الهيكل يلغي مشاكل CORS تمامًا لأن المتصفح يتعامل مع نطاق واحد فقط.


‏* **3. معالجة وتخزين النقاط:** يستقبل تطبيق FastAPI الطلب ويفحص سلامة البيانات عبر مكتبة Pydantic (تحديد طول الاسم والحد الأقصى للنقاط). ثم يتصل بـ Redis عبر اسم الخدمة `redis` المحدد في الـ ConfigMap.


‏* **4. إدارة لائحة الصدارة (Leaderboard):** يُخزن FastAPI أعلى نتيجة فقط لكل لاعب باستخدام أمر `zadd` الخاص بالـ Sorted Sets في Redis. ويقوم بتحديد حجم القائمة تلقائيًا عبر `zremrangebyrank` لضمان عدم تضخم قاعدة البيانات.


‏* **5. عرض المتصدرين:** يستعلم المتصفح بطلب `GET /api/leaderboard` لجلب أفضل 5 لاعبين مجلبين بأمر `zrevrange` بالترتيب التنازلي.

‏**خصائص الاعتمادية والهندسة المتقدمة**

‏* **التوسع واستمرارية الخدمة:** تم تشغيل نسختين (2 Replicas) لكل من Frontend و Backend لضمان عدم توقف اللعبة عند تحديث النسخ أو الضغط العالي.


‏* **استدامة البيانات:** تعتمد قاعدة بيانات Redis على `PersistentVolumeClaim` مرتبطة بـ `StorageClass` مخصص يُدعى `snake-local-path` بسياسة الاحتفاظ `Retain` لمنع مسح بيانات الصدارة في حال حذف الحاوية بالخطأ.


‏* **فحوصات الجاهزية والصحة (Probes):** يتيح الـ Backend مسارين: `/api/health` للـ Liveness (تأكيد عمل الحاوية) و `/api/ready` للـ Readiness (لا توجَّه الحركة للحاوية إلا إذا كان Redis متصلاً وجاهزًا).


‏* **بيئة الاختبار والمحاكاة:** يحتوى المشروع على بيئة اختبارات آلية مكتملة بـ Pytest تستخدم `fakeredis` لمحاكاة قاعدة البيانات في الذاكرة لضمان اختبار الكود بنسبة تغطية تتجاوز 80% دون الحاجة لتشغيل Redis حقيقي.

‏-1.الخلفية (Backend - FastAPI)**

‏* **Readiness (`/api/ready`):** يفحص الاتصال بـ Redis كل 10 ثوانٍ؛ يرجع `503` إذا توقفت قاعدة البيانات ليوقف K8s توجيه حركة المرور للحاوية مؤقتًا دون إعادة تشغيلها.


‏* **Liveness (`/api/health`):** يفحص قيام عملية Python كل 15 ثانية؛ يرجع `200 OK` ليمنع K8s من إعادة تشغيل الحاوية عند حدوث خلل مؤقت في Redis.


‏* **مواقع الكود:** `backend/app/main.py`، و `k8s/game-api-deployment.yaml`، و `backend/Dockerfile`.



‏**الواجهة الأمامية (Frontend - Nginx)**

‏* **Readiness & Liveness (`/healthz`):** يُرجع Nginx مباشرة `200 ok` دون كتابة سجلات (Logs) ليرسخ جاهزيته لنقل حركة المرور وعرض الصفحات.


‏* **مواقع الكود:** `frontend/nginx.conf`، و `k8s/frontend-deployment.yaml`، و `frontend/Dockerfile`.



‏**المُنفّذ الفعلي للفحوصات**

‏* **Kubernetes (عبر `kubelet`):** هو المبادر بإرسال طلبات الـ HTTP واتخاذ قرار العزل أو إعادة التشغيل.


‏* **Nginx / FastAPI:** يقتصر دورهما على الاستجابة فقط للطلبات الواردة من K8s.
